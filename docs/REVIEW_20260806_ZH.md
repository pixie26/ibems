# IB Execution Platform Phase 0 独立审查

日期：2026-08-06  
审查对象：用户上传的 `ib-execution-platform-v0.1.0-phase0`

## 一、结论

计划本身方向正确，特别是以下排序应保留：

1. 现有数据先完成经济性 Gate A；
2. 全时段只读 recorder 同时启动，积累不可回补的尾部日样本；
3. 执行平台以 FakeBroker 和故障恢复为核心，而不是先接 IB；
4. Paper 只验证 IB 协议行为，不验证真实滑点；
5. Shadow 必须通过 L1/L2/L3；
6. 最小 live 是成本采样实验，不是资金部署。

但上传版本不能按 README 所称视为“Gate B1 已完成”。原始实现存在数个会直接破坏安全不变量的问题，且“21 条不变量均具备 property test、runtime assertion、journal auditor”这一声明不成立。

审查后的状态应定义为：

> **Phase 0 核心原型可继续；Gate B1 尚未通过；严禁连接 Paper 或 Live。**

## 二、原始实现中的关键问题

### Critical 1 — 正常下单路径自相矛盾

原代码在 `place_order()` 前把 `order_state` 设为 `SUBMISSION_UNCERTAIN`。耦合规则随后把 `sync_state` 降为 `UNVERIFIED`，而下一行运行时断言又要求 broker write 必须处于 `SYNCED`。

结果：正常下单路径必然触发 invariant 6。

修正：

- 正常调用期间进入 `PENDING_ACK`；
- 只有 broker 调用结果不确定，或重启时发现 `SEND_ATTEMPT_STARTED` 没有可证明的终态，才进入 `SUBMISSION_UNCERTAIN`。

### Critical 2 — 重启后已有 working order 未恢复为 working

原 reconciliation 只恢复 `working_signed`，但可能保留：

```text
order_state = IDLE
live_intent = None
```

此时新 target 会把 broker 已有订单当作不存在，产生第二张相反方向订单。

修正：对 broker snapshot 中每张已归属的 open order，从 durable intent 重建：

```text
live_intent
order_state = WORKING
working_signed
orderId / permId
attempt
```

并增加回归测试：重启后已有 BUY 3，target 改为 0，只能 cancel BUY，不得同时再发 SELL。

### Critical 3 — 外部订单归属只检查 strategy 前缀

原 `_is_ours()` / callback fallback 可把：

```text
manual_test|forged|...
```

误认为平台订单。这违反独占账户和零容忍归属原则。

修正：

- 只接受与 journal 中 durable `orderRef` 精确匹配的事实；
- 已知 `permId` 时同时核对 `permId`；
- 未知 callback、execution、fee 均触发 `UNVERIFIED + HALTED`；
- 不再通过 strategy prefix 猜归属。

### Critical 4 — 外部 execution callback 可被静默收养

原 callback 路径先把 execution 写入 journal，之后才尝试找 leg。外部成交因此进入 expected position；下一次 reconciliation 反而会认为 position 已被解释。

修正：execution 入账前先验证 durable identity；无法归属则 HALT，绝不写入 position ledger。

### Critical 5 — 断线状态仍会尝试 cancel

原 reprice timer 到期时可在 `DISCONNECTED/UNVERIFIED` 下调用 `cancel_order()`，制造“风险正在被降低”的假象。

修正：place 和 cancel 使用同一个 write gate：

```text
link == CONNECTED
sync == SYNCED
```

否则只告警并等待 reconciliation，不产生 broker write。

### Critical 6 — 1101 后一条 quote 即恢复交易

原逻辑可能在市场数据丢失后，收到一条 quote 就把 link 恢复为健康，而没有证明所有订阅已恢复，也没有重新对账。

修正：

```text
on_market_data_lost()      -> DEGRADED + UNVERIFIED
on_quote()                 -> 只存 quote，不恢复状态
on_market_data_restored()  -> CONNECTED + UNVERIFIED
reconcile()                -> 成功后才 SYNCED
```

### Critical 7 — 两个 idempotency 崩溃窗口

原顺序分别为：

```text
claim decision_id -> commit TARGET_RECEIVED
claim execId      -> commit EXECUTION_RECEIVED
```

两步之间崩溃会造成：

- decision 已永久消费，但没有 accepted target 事件；
- execId 已永久占用，但 position ledger 没有成交。

修正：两组动作分别改成单一 SQLite 事务：

```text
consume decision_id + append TARGET_RECEIVED
claim execId + append EXECUTION_RECEIVED
```

### Major 1 — 拒单循环不计入速率熔断

原代码只有 `place_order()` 成功返回后才增加 order counter。若 broker 持续 clean reject，自动系统可无限重试而永远不触发 `max_orders_per_minute`。

修正：所有 broker submission attempt，包括 clean rejection，都计入订单频率、累计股数和名义金额上限。

重启后的计数从 `SEND_ATTEMPT_STARTED` 重建，而不是从 `SEND_CALL_RETURNED` 重建。

### Major 2 — asyncio/fsync 的论证不成立

Journal 的 SQLite syscall 虽在 writer thread 执行，但 `commit()` 仍同步等待 `threading.Event`。若 Controller 直接运行在 `ib_async` event loop，event loop 仍会被 fsync 延迟阻塞。

修正：新增 `AsyncControllerBridge`：

```text
IB event loop
    -> FIFO asyncio queue
    -> 单一 controller worker thread
    -> synchronous Controller + Journal
```

这样同时保留：

- event loop 不被 durable write 阻塞；
- controller 仍是单 writer；
- callback 顺序可控；
- Phase 0 可完全同步、确定性测试。

该 bridge 在 Gate B2 前必须接入 IbAdapter 并进行过载、异常和关闭测试。

### Major 3 — 风控配置文件实际上没有被加载

原 repo 提供 `risk.example.yml`，但 preflight 使用的是代码默认 `RiskConfig()`，所以实际部署配置与自检配置可以完全不同。

修正：新增严格 YAML loader：

- 未知字段拒绝；
- Decimal 明确转换；
- whitelist 必须为 list；
- `${ENV}` 未定义则拒绝；
- preflight 必须加载实际 risk config；
- 每个 intent 保留 config hash。

### Major 4 — invariant 19 只是布尔声明

原配置只有 `overnight_survivable: true`，无法证明仓位真的可承受隔夜跳空。

修正为数值约束：

```text
overnight_gap_stress_pct
max_overnight_loss
```

每一笔增加风险的订单均计算：

```text
abs(resulting_position) × mid × stress_pct
```

超过预算则拒绝。

### Major 5 — Recorder 日检会漏报

原 `compute_health()`：

- 只使用最后一个 `market_data_type`；中间 DELAYED、最后 LIVE 会误报通过；
- SYSTEM heartbeat 参与 gap 计算，可掩盖真实行情断档；
- 同日重启后 segment 文件名可能碰撞覆盖。

修正：

- 任何混合数据类型均报告 `MIXED`；
- gap/coverage 只使用 market events；
- SYSTEM heartbeat 不得填补行情空洞；
- segment 文件名加入随机 `run_id`。

### Major 6 — Auditor 的完成度被高估

原 auditor 实际只覆盖部分不变量，且：

- `_require()` 并未广泛用于 21 条 runtime invariants；
- 错误 journal 路径会被自动创建为空 DB，并打印 PASS；
- `SEND_CALL_FAILED(uncertain)` 被错误当作 intent terminal；
- cancel write 未纳入 link/sync 审计。

修正：

- 缺失或空 journal 直接 FAIL；
- 明确打印“partial coverage”；
- 当前 journal 可观察的 14 条进入 auditor；
- 其余 7 条在 coverage matrix 中标为未完成；
- 不再声称 Gate B1 已满足 invariant 20。

## 三、审查中已完成的代码修改

1. `PENDING_ACK` / `SUBMISSION_UNCERTAIN` 语义分离；
2. 重启 working order 完整 rehydrate；
3. cancel 经过 link/sync write gate；
4. 1101 恢复需显式 resubscribe + reconcile；
5. exact `orderRef` + `permId` 归属；
6. 外部 live execution 不得静默入账；
7. target acceptance 和 execution booking 原子化；
8. broker rejects 纳入 runaway counters；
9. 日内 counters 从 journal 恢复；
10. 数值化 overnight stress；
11. 严格 YAML risk config loader；
12. compact hashed `orderRef`，避免依赖未验证的 broker 截断行为；
13. recorder health 修复；
14. `AsyncControllerBridge`；
15. auditor 缺失/空 DB fail-closed，并明确覆盖范围；
16. 新增 12 个独立审查回归测试及相关 recorder/config/bridge 测试。

## 六、最终判断

上传版本不是低质量实现。它已经抓住了 target-position、WAL、reconciliation、single writer、fault injection 等真正重要的架构原则。

问题在于：README 把“规格写清楚”和“规格已被实现证明”混为一谈。执行系统里，这是危险的完成度错觉。

本审查包已修复当前可复现的核心安全 bug，并把状态从：

```text
Phase 0 implemented and tested
```

改为更准确的：

```text
Phase 0 core prototype under review
Gate B1 not yet passed
No IB connection permitted
```
